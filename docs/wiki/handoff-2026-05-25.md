### Vulnérabilité droppée — détail

`brh_agence_audits.agence_audits_respond_anon` autorisait `UPDATE TO anon USING (true) WITH CHECK (true)` **sans validation du `response_token`**. Un anonyme pouvait UPDATE n'importe quelle ligne d'audit. Aucune route `/audit/respond?token=xxx` n'existe côté frontend → policy **inutilisée** → DROP safe.

**Si la feature audit-respond est réactivée** : créer RPC SECURITY DEFINER `brh_audit_respond(p_token, p_feedback, p_feedback_message)` qui valide le token avant UPDATE, puis GRANT EXECUTE à anon.

## 🟡 Reste à faire — C3 BDNB Bretagne (le seul item reporté)

### Pourquoi reporté
- Chantier 5-10h
- Aucune des 22 règles V2 actuelles ne consomme BDNB → impact indirect seulement (futures règles typologie bâti : % vitrage, matériaux, étages)
- Volume : 4 zips de 600-750 MB = 2.4 GB compressé / ~40 GB décompressé
- Format = SQL plain avec PostGIS, 56 tables par département
- Supabase Pro plafonne à 8 GB DB

### Recette d'ingestion minimale (pour future session)

1. **Setup Docker PostgreSQL+PostGIS local** :
   ```bash
   docker run -d --name bdnb-pg \
     -e POSTGRES_PASSWORD=brh \
     -p 5433:5432 \
     postgis/postgis:15-3.4
   ```

2. **Restore BDNB par dept** (1-2h chacun, 4 dépts) :
   ```bash
   cd /opt/stack/bdnb-bretagne/raw
   for dep in 22 29 35 56; do
     unzip -o dep${dep}.pgdump.zip -d /tmp/bdnb-${dep}/
     PGPASSWORD=brh psql -h localhost -p 5433 -U postgres -d postgres \
       -f /tmp/bdnb-${dep}/pgdump/bdnb.sql > /tmp/bdnb-${dep}-restore.log 2>&1
   done
   ```

3. **Identifier les 5-10 colonnes utiles pour scoring V2 BRH** (depuis `documentation.xlsx`) :
   - Table cible : `batiment_groupe_dpe_representatif_logement`
   - Colonnes candidates : `surface_habitable_logement`, `annee_construction`, `materiaux_structure_mur`, `materiaux_toiture`, `nombre_niveau`, `presence_vitrage_double`, `score_renovation_potentielle`
   - + Table `rel_batiment_groupe_adresse` → lien BAN id pour matching avec nos DPE

4. **Extract CSV minimaliste** :
   ```bash
   PGPASSWORD=brh psql -h localhost -p 5433 -U postgres -d postgres <<SQL
   COPY (
     SELECT bg.batiment_groupe_id,
            bga.cle_interop_adr AS ban_id,
            bg_rep.surface_habitable_logement,
            bg_rep.annee_construction,
            bg_rep.materiaux_structure_mur
     FROM bdnb_2025_07_a_open_data_dep22.batiment_groupe bg
     JOIN bdnb_2025_07_a_open_data_dep22.batiment_groupe_adresse bga ON bg.batiment_groupe_id = bga.batiment_groupe_id
     LEFT JOIN bdnb_2025_07_a_open_data_dep22.batiment_groupe_dpe_representatif_logement bg_rep ON bg.batiment_groupe_id = bg_rep.batiment_groupe_id
   ) TO '/tmp/bdnb-22-extract.csv' WITH CSV HEADER;
   SQL
   ```
   Volume estimé : ~150-300 MB par dept → 600 MB-1.2 GB total CSV (acceptable dans Supabase 8 GB).

5. **Création table cible Supabase** :
   ```sql
   CREATE TABLE brh_ext_bdnb_batiments (
     batiment_groupe_id TEXT PRIMARY KEY,
     ban_id TEXT,
     surface_habitable NUMERIC,
     annee_construction INTEGER,
     materiaux_structure_mur TEXT,
     materiaux_toiture TEXT,
     nombre_niveau INTEGER,
     presence_vitrage_double BOOLEAN,
     dept VARCHAR(2)
   );
   CREATE INDEX brh_ext_bdnb_ban_id_idx ON brh_ext_bdnb_batiments (ban_id) WHERE ban_id IS NOT NULL;
   ```

6. **Upload via Supabase Storage + COPY** (4 CSV en batch) :
   - Storage bucket dédié `bdnb-csv` (signed URL temp)
   - RPC SECURITY DEFINER qui fait `COPY FROM` (Supabase ne supporte pas COPY direct via API)

7. **Ajouter nouvelles règles V2 si pertinentes** :
   - Ex : `r_vitrage_simple` = +5 pts si `presence_vitrage_double = FALSE AND annee_construction < 1990`
   - Ex : `r_pierre_ancienne` = +3 pts si `materiaux_structure_mur = 'pierre' AND annee_construction < 1900`

**Estimation totale** : 5-10h selon découvertes BDNB. À planifier en sprint dédié.

## ⚠️ Dette technique zéro mais pièges à connaître

### Règles anti-saturation DB (non négociables)

1. **JAMAIS regex full-scan** sur grande table (utiliser colonne générée + index)
2. **JAMAIS batches concurrents lourds** sur même DB (incident 24/05 : IRIS+BAN concurrents → crash IRIS, relancé seul OK)
3. **TOUJOURS index** sur WHERE/JOIN si table > 50k rows
4. **Migration corrective** = colonne générée STORED
5. **Si saturation** : STOP batches + analyser, pas restart en boucle
6. **UPDATE bulk > 100k rows** = timeout 2 min Supabase API → batcher par dept ou par range d'IDs
